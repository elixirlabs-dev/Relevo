# Receipt format: `elivo-receipt-1`

> **Testnet prototype. Payout firms and SPEI receipts are simulated. Contract unaudited.**

Each funded batch ends with a signed receipt. The receipt records every payout: its amount, which firms held it, when it was delivered or why it was refunded, any penalty the late firm paid, and the transaction hashes. Its hash is anchored in the escrow contract, so anyone can check the receipt against the chain without trusting the operator.

This folder publishes the format so that tools in any language can check receipts:

| File | What it is |
|---|---|
| [`elivo-receipt-1.schema.json`](elivo-receipt-1.schema.json) | JSON Schema (draft 2020-12) for the receipt file |
| [`vectors/`](vectors/) | Test vectors and a `manifest.json` with the expected verdict and hash for each |

A real anchored receipt from the testnet reference run (batch 5) is at [`apps/web/public/receipts/testnet-batch-5.json`](../../apps/web/public/receipts/testnet-batch-5.json).

## Fields

- **Amounts:** USDC base units (6 decimals) as decimal strings: `"1000000000"` is 1,000 USDC. `amount_mxn` is the MXN amount exactly as written in the payee CSV (0 to 2 decimals, e.g. `37000` or `37000.50`), or empty if the router had no row for the payout.
- **Times:** `*_ns` fields are NEAR block times in nanoseconds since the Unix epoch, as strings.
- **Payees:** never named. `payee_ref` is `sha256(salt ‖ CLABE)` in hex, and `clabe_last4` is the last 4 digits. The salt stays with the operator.
- **State:** `Delivered`, or `Refunded` (`excluded: true` with a `reason` such as `ACCOUNT_CLOSED` means the account was closed and no penalty applies).
- **Penalties:** `penalties_total` is what the late firm's bond paid to the funder (the DAO) for that payout.
- **Totals**, recomputable from the rows:
  - `locked` = Σ (amount + 25 bps fee buffer);
  - `paid_to_firms` = Σ over delivered payouts of (amount + amount × `quote_bps` / 10,000);
  - `penalties` = Σ `penalties_total`;
  - `returned_to_funder` = `locked` − `paid_to_firms` + `penalties`.

## Signing and the anchored hash

1. **Body:** the receipt without its `signature` field.
2. **Canonical bytes:** the body serialised with the [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) JSON Canonicalization Scheme, as UTF-8.
3. **Signature:** ed25519 over those bytes, stored as `signature.sig` (base64), with `signature.public_key` as `ed25519:<base58>`.
4. **Anchored hash:** `base58(sha256(RFC 8785 bytes of the whole receipt, signature included))`. The router writes it to the escrow with `anchor_receipt`. `get_batch` returns it as `receipt_hash`, together with the batch's `receipt_pk`.

## How to verify a receipt

Never trust the key or escrow written in the file. Take them from the chain:

1. Choose the escrow account yourself. Call its view method `get_batch({"batch_id": <batch_id>})`.
2. Check that `signature.public_key` equals the batch's `receipt_pk`, and that the ed25519 signature verifies over the canonical body.
3. Check that the anchored hash computed from the file equals the batch's `receipt_hash`.
4. Recompute the totals from the rows.

Three ways to do this here:
- **In the browser:** the web app's `/verify` page runs all four checks and then offers a CSV export.
- **Command line:** `pnpm verify-receipt <file> --chain --rpc <url> --escrow <account>`.
- **Code:** `packages/shared/src/receipt-web.ts` (browser-safe, WebCrypto) and `packages/shared/src/receipt.ts` (Node).

## Test vectors

`vectors/manifest.json` lists each case:
- the file;
- the public key to verify it with;
- the expected verdict: `ok`, `bad_signature`, `key_mismatch` or `malformed`;
- the anchored hash, where there is one.

A verifier is compatible when it returns the same verdict and hash for every entry.

The vectors use fictitious accounts and a fixed test key, and are generated by `pnpm gen:vectors`. The test suite checks that the committed files match the generator byte for byte, and that both verifiers agree with the manifest.

## CSV export

The CSV export (from `/verify`) has one row per payout:
- USDC values with 6 decimals, ISO 8601 UTC times;
- the batch id and receipt hash on every row, so a row stays traceable after import;
- RFC 4180 quoting with CRLF line endings, and a leading `'` on any cell that starts with `=`, `+`, `-` or `@`.

# Receipt format: `elivo-direct-receipt-1`

A receipt for payouts an issuer (a grant programme, a payroll platform, a payout provider) **made itself, outside the escrow, on any rail**. The issuer signs it, and its hash is anchored in the receipt registry contract (`contracts/registry`) under the issuer's own account.

| File | What it is |
|---|---|
| [`elivo-direct-receipt-1.schema.json`](elivo-direct-receipt-1.schema.json) | JSON Schema (draft 2020-12) |
| [`apps/web/public/receipts/testnet-direct-payroll.json`](../../apps/web/public/receipts/testnet-direct-payroll.json) | A real receipt anchored on testnet, from invented payout data (ed25519) |
| [`apps/web/public/receipts/testnet-direct-payroll-pq.json`](../../apps/web/public/receipts/testnet-direct-payroll-pq.json) | The same payouts, signed with ed25519 and ML-DSA-65 under the issuer's key version 2 |

What it proves, and what it doesn't: that the issuer's account published this exact list of payouts at a given time and can't change it afterwards. It does not prove that a bank carried out each transfer; that needs a bank-side source such as Mexico's CEP, which is on the roadmap.

## Fields

- `registry`, `issuer`, `receipt_id`: where the hash is anchored, by whom, and under which id (1–64 of `A-Z a-z 0-9 . _ -`). An issuer can't reuse an id.
- `rail` and `currency`: for example `SPEI` and `MXN`. On the SPEI rail every account is checked as a CLABE before the receipt is built.
- Each payout: `payee_ref` = `sha256(salt ‖ account)` in hex (the salt stays with the issuer), `account_last4`, `amount` (two decimal places), `status` (`Paid`, `Returned` or `Failed`), `paid_at` (ISO 8601 UTC) and `reference` (the rail's own reference, or why the payout wasn't made).
- `totals`: `count`, `paid` (sum of `Paid` amounts) and `not_paid` (the rest), recomputable from the rows.
- `signatures`: a list. It holds one ed25519 signature, plus an ML-DSA-65 (FIPS 204, post-quantum) signature when the issuer has published an ML-DSA-65 key. For ML-DSA-65, `public_key` is the 1,952-byte key in base64 and `sig` the 3,309-byte signature in base64.

## Signing and the anchored hash

1. **Signed bytes:** the RFC 8785 canonical JSON of the receipt without its `signatures` field.
2. **Anchored hash:** `base58(sha256(canonical JSON of the whole receipt, signatures included))`, written with the registry's `anchor(receipt_id, receipt_hash)`.
3. **Post-quantum signature:** ML-DSA-65 (pure, not pre-hashed) over the same bytes, with the FIPS 204 context string `elivo-direct-receipt-1`, so the signature can't be reused for anything else.
4. **Keys:** the issuer publishes them with `set_keys(receipt_pk, mldsa65_pk)`. Keys are versioned, and each anchor records the version in force, so rotating a key never changes how an older receipt verifies.

## How to verify

1. Choose the registry account yourself, and call `get_receipt({"issuer": <issuer>, "receipt_id": <receipt_id>})`.
2. Check that the ed25519 signature is by the returned `receipt_pk`. If `mldsa65_pk` is set, the receipt must also carry an ML-DSA-65 signature by that key, and it must verify; if it isn't set, the receipt must not carry one.
3. Check that the hash of the file equals the returned `receipt_hash`.
4. Recompute the totals.

`/verify` in the web app runs all four. On the command line: `pnpm verify-receipt <file> --chain --rpc <url> --registry <account>`.

## Issuing one

```bash
pnpm issue-receipt samples/payroll-results.csv --id <receipt-id> --issuer <your-testnet-account>
```

Add `--pq` to sign with ML-DSA-65 as well; the command creates the post-quantum key on first use and publishes it with your ed25519 key. The results CSV has the columns `name,account,amount,status,paid_at,reference`. Names and full account numbers never leave your machine. The command publishes your receipt key if needed, signs, anchors, and writes the receipt and its salt to `.data/receipts/`.

# Receipt format: `elivo-direct-receipt-2` and payee proofs (`elivo-payee-proof-1`)

> **Testnet prototype. Payout firms and SPEI receipts are simulated. Contract unaudited.**

Version 2 of the direct receipt lets each payee check **their own payout** against the registry without seeing anyone else's. The issuer signs and anchors a header that commits to all payouts through a Merkle root. Each payee gets a small proof file containing the signed header, their payout row, the Merkle path from that row to the root, and their own salt.

| File | What it is |
|---|---|
| [`elivo-direct-receipt-2.schema.json`](elivo-direct-receipt-2.schema.json) | JSON Schema (draft 2020-12) for the full receipt |
| [`elivo-payee-proof-1.schema.json`](elivo-payee-proof-1.schema.json) | JSON Schema (draft 2020-12) for one payee's proof |

Version 1 receipts are unchanged and keep verifying as before.

## Header and payouts

The receipt is a **header** plus `signatures` plus `payouts`. The header holds every `elivo-direct-receipt-1` field except `payouts` (`label`, `network`, `registry`, `issuer`, `receipt_id`, `generated_at`, `rail`, `currency`, `totals`), with `version: "elivo-direct-receipt-2"` and three new fields:
- `payouts_root`: the Merkle root over the payouts, in hex;
- `payout_count`: the number of payouts;
- `check_ref`: `{ "report_id", "report_hash" }` of the pre-payout check report, or `null`.

Payout rows have the same fields as in v1. A payout's `id` is its position (0, 1, 2, ...).

## Merkle tree

- **Leaf:** `sha256(0x00 ‖ RFC 8785 canonical JSON of the payout row)`.
- **Internal node:** `sha256(0x01 ‖ left ‖ right)`. The prefixes stop a leaf from passing as a node.
- **Odd node:** at any level, a last node without a partner is carried up unchanged (it is not duplicated).
- **One payout:** the root is that payout's leaf.
- **Proof:** `siblings` lists the sibling hashes from the leaf up. `side: "L"` means the current hash becomes `sha256(0x01 ‖ sibling ‖ current)`, and `side: "R"` means `sha256(0x01 ‖ current ‖ sibling)`. A level where the node was carried up has no entry.

## Payee references

Each payee gets their own salt, derived from a per-receipt salt that only the issuer keeps:
- `payee_salt_i = sha256(receipt_salt ‖ uint32be(i))`;
- `payee_ref_i = hex(sha256(payee_salt_i ‖ utf8(account)))`.

A payee proof reveals `payee_salt_i` and nothing else. The other payees' salts can't be derived from it, so a proof doesn't help anyone link the other rows to accounts.

## Signing and the anchored hash

1. **Signed bytes:** the RFC 8785 canonical JSON of the header, with no `payouts` and no `signatures`.
2. **Signatures:** the same as v1. One ed25519 signature, plus ML-DSA-65 with the FIPS 204 context string `elivo-direct-receipt-1` when the issuer has published an ML-DSA-65 key.
3. **Anchored hash:** `base58(sha256(canonical JSON of the header plus signatures))`, which is the receipt without `payouts`. It is written with the registry's `anchor(receipt_id, receipt_hash)`, exactly as in v1.

Because neither the signatures nor the anchor cover the rows directly, the header alone (inside a payee proof) can be checked against the chain. The rows are bound through `payouts_root`.

## How to verify a v2 receipt

1. Choose the registry account yourself, and call `get_receipt({"issuer": <issuer>, "receipt_id": <receipt_id>})`.
2. Check the signatures over the signed bytes against the returned `receipt_pk`, and against `mldsa65_pk` when it is set. These are the same rules as v1.
3. Check that the anchored hash computed from the file equals the returned `receipt_hash`.
4. Recompute `payouts_root` from the rows, check that `payout_count` equals the number of rows and that the ids run 0..n−1, and recompute the totals.

## How to verify a payee proof

1. Do steps 1 to 3 above, using the proof's `header`.
2. Recompute the leaf from `payout` and follow `proof.siblings` up to `header.payouts_root`. Check that `payout.id` equals `proof.index`, that the index is below `payout_count`, and that the sides fit that index in a tree of `payout_count` leaves.
3. **Payee only:** check that `sha256(payee_salt ‖ utf8(your account))` equals `payout.payee_ref` and that `account_last4` matches.

On the command line, either file works. The output names the format:

```bash
pnpm verify-receipt <receipt.json> --chain --rpc <url> --registry <account>
# OK (elivo-direct-receipt-2, 5 payouts)
pnpm verify-receipt <proof.json> --chain --rpc <url> --registry <account> [--account <your CLABE>]
# OK (elivo-payee-proof-1, payout 3 of 5 in <issuer>/<receipt_id>)
```

In code: `packages/shared/src/direct-receipt-v2.ts` and `packages/shared/src/merkle.ts` (both browser-safe).

## Issuing one

```bash
pnpm issue-receipt samples/payroll-results.csv --id <receipt-id> --issuer <your-testnet-account> --v2 [--pq]
```

This writes three things to `.data/receipts/`:
- the receipt, `direct-<issuer>-<id>.json`;
- one proof per payee, `direct-<issuer>-<id>.payee-<i>.json`. Give each payee only their own;
- the receipt salt, `direct-<issuer>-<id>.salt` (mode 0600).

The command also prints the receipt salt once. It is a secret: with it, anyone holding a list of candidate accounts can link every row to a payee. Keep it with your records and never publish it.
